# 21_车机监控与日志采集

> 基线：2026-11-08
> 适用：库斯途车机（SABRESD-MX6DQ，Android 4.4.3，armeabi-v7a，**已 root**）
> 关联：`19_C3端代码质量审查.md`、`20_Reborn端代码质量审查.md`、`13_原厂三包与仪表投影分析.md`

---

## 1. 目的

仪表投影类问题（闪动、箭头与罗盘交替、左右相反、限速牌跳变）往往**同时涉及四个进程**：

```
百度 CoDriver / 百度地图 ──┐
高德车机版 ───────────────┼──► HSAE 车机服务 ──► 原厂仪表
Reborn（本 App）──────────┘
```

单看任何一方的日志都不足以定位。本方案一次性把**四方日志 + 内核 Binder 事务 + 前台状态**
在同一时间轴上抓全，事后按时间戳对齐分析。

## 2. 脚本清单

| 脚本 | 位置 | 运行端 | 需要 root | 适用 |
|---|---|---|---|---|
| `scripts/device/cluster_monitor.sh` | 车机 `/data/local/tmp/` | 车机 | ✅ | **推荐**。含 Binder 事务、可后台长跑 |
| `scripts/monitor_cluster_baidu.sh` | PC | PC（adb） | ❌ | 临时快速抓取、无需 root |

两者产物结构一致，差别只在数据来源：车机端能读 `/sys/kernel/debug/binder`，PC 端不能。

## 3. 车机端：部署与使用

### 3.1 部署

```bash
adb -s <车机IP>:5555 push scripts/device/cluster_monitor.sh /data/local/tmp/cluster_monitor.sh
adb -s <车机IP>:5555 shell "su -c 'chmod 755 /data/local/tmp/cluster_monitor.sh'"
```

> **必须保持 LF 换行**。仓库已通过 `.gitattributes`（`*.sh text eol=lf`）固定；
> 若手工编辑过脚本，先转换：`sed -i 's/\r$//' scripts/device/cluster_monitor.sh`。

### 3.2 启停

```bash
# 开始采集（分钟数，默认 30；第二参数是落盘时间戳，建议用 PC 时间避免车机时钟偏差）
STAMP=$(date +%Y%m%d_%H%M%S)
adb shell "su -c 'sh /data/local/tmp/cluster_monitor.sh start 30 $STAMP'"

# 查看状态
adb shell "su -c 'sh /data/local/tmp/cluster_monitor.sh status'"

# 停止：补最后一次 Binder 增量、生成分类文件与摘要、打包 tar.gz
adb shell "su -c 'sh /data/local/tmp/cluster_monitor.sh stop'"
```

### 3.3 取回

```bash
adb pull /sdcard/cluster_mon/<STAMP>
# 或直接取压缩包
adb pull /sdcard/cluster_mon/<STAMP>.tar.gz
```

## 4. 日志目录与文件说明

车机端路径：**`/sdcard/cluster_mon/<时间戳>/`**（文件管理器可见，也可 U 盘拷出）

| 文件 | 内容 | 用途 |
|---|---|---|
| **`binder_chain.txt`** | Binder 事务 + **已解析进程名** | **最完整的数据链路**：`com.baidu.che.codriver -> com.hsae.core size=192` |
| `binder_transactions.txt` | 内核 Binder 事务原始行（带全局序号） | 精确排序、按 code/size 过滤 |
| `binder_pids.txt` | 周期性 `ps` 快照 | pid 随重启变化时回溯对应进程 |
| `pid_map.txt` | pid → 进程名 | 自行解析事务时用 |
| `logcat.txt` | main / system / events 三缓冲，`threadtime` 格式 | 全量上下文 |
| `baidu.txt` | 百度系（codriver / mapauto / carlife） | 看百度如何触发仪表 |
| `amap.txt` | 高德系（amapauto、AUTONAVI 广播） | 对照高德链路 |
| `hsae.txt` | HSAE 系统（`IBINDER_`、`autosdk`、`INavigation`） | 看仪表服务侧反应 |
| `reborn.txt` | Reborn 自身 + `ClusterDbg` 发帧诊断 | 我们发了什么帧、为什么发 |
| `dumpsys.txt` | 每约 25 秒：前台应用、窗口焦点、相关广播 | 把现象与"当时谁在前台"对齐 |
| `meta.txt` | 设备、各 App 版本、进程表、Reborn 设置 | 复现环境记录 |
| `errors.txt` | FATAL / ANR / ClassCastException / W/Bundle | 快速看异常 |
| `summary.md` | 自动统计（各文件行数、发帧分布、KEY_TYPE 分布、调用链 Top20） | 分析入口 |
| `<STAMP>.tar.gz` | 上面全部内容 | 一包带走 |

## 5. Binder 事务日志怎么读

内核 debugfs 提供（需 root）：

```
/sys/kernel/debug/binder/transaction_log      # 环形缓冲，全部事务
/sys/kernel/debug/binder/failed_transaction_log
/sys/kernel/debug/binder/stats
```

原始行格式：

```
718629: async from 1145:1145 to 151:0 node 247665 handle 17 size 80:0
   │      │      │            │       │            │      └─ 数据/对象大小
   │      │      │            │       │            └─ handle
   │      │      │            │       └─ 目标 node
   │      │      │            └─ 目标 pid:tid
   │      │      └─ 源 pid:tid
   │      └─ call / async / reply / oneway
   └─ 全局序号（单调递增，用于去重与排序）
```

脚本按**序号增量去重**，因此不会因环形缓冲覆盖而丢数据或重复计数。

`binder_chain.txt` 中已翻译为：

```
718629  1145(com.rair.adbwifi) -> 151(surfaceflinger)  async  size=80:0
```

**定位百度→仪表链路**：筛 `baidu` 与 `hsae` 关键字，例如

```bash
grep -E 'com\.baidu|com\.hsae' binder_chain.txt | head -50
```

> 局限：debugfs 只记录**调用元信息**（谁调谁、多大、哪种类型），**不含 Payload 内容**。
> 需要看具体字段时，只能依赖各方自己的日志（`baidu.txt` / `hsae.txt`）或标定脚本逐帧试发。

## 6. 典型分析流程

### 6.1 仪表闪动 / 数值跳变

1. 看 `reborn.txt`：`[TBT] type=… reason=changed|keepalive` 的密度与 `displayType`
2. 若同一 `type` 高频 `keepalive` → 保活重发导致重绘
3. 若 `type` 在 `8`（罗盘）与箭头之间反复 → 判定条件在两端抖动（见 20 号 R 系列修复记录）

### 6.2 左右方向相反

1. `reborn.txt` 找 `[NAVI] … tbtIcon=N`
2. 对照 `ClusterMapper.mapTurnType` 的映射，再用标定脚本验证 HSAE 码位语义：

```bash
./scripts/calibrate_cluster.sh --seq 67    # HSAE 67 应显示"右转"
./scripts/calibrate_cluster.sh --seq 70    # HSAE 70 应显示"左转"
```

3. 若仪表实际显示与码位表相反 → 修正映射（20 号文档已按实车观察做左右镜像）

### 6.3 未导航时没有罗盘

1. `reborn.txt` 看收到的 `RX keyType=`：
   - 只有 `12205`（定位，`EXTRA_GEOLOCATION` 为整数 0）与 `10019/13022` → 高德**未发导航数据**
   - 出现 `10001` 且含 `CAR_DIRECTION` → 高德在导航
2. 结论：高德纯地图态不提供航向，需用**车机 GPS** 兜底（见 20 号文档 R 系列实现）

### 6.4 广播时序

`dumpsys.txt` 每 25 秒记录 `dumpsys activity broadcasts` 的相关片段，
可与 `baidu.txt`/`amap.txt` 的时间戳对齐，确认"谁在何时触发"。

## 7. 实现要点（Android 4.4 的坑）

| 问题 | 现象 | 处理 |
|---|---|---|
| 工具缺失 | 无 `head/tail/awk/sed/wc` | 统一走 `/system/bin/busybox <applet>` |
| `id -u` 不可用 | toolbox 版 `id` 不支持 `-u`，脚本误判非 root | 改用 `busybox id -u` |
| 后台进程存活 | `adb shell`/`su -c` 退出即 SIGHUP，采集任务被杀 | `busybox setsid` 脱离会话 + 重定向 stdin/stdout |
| logcat 探活 | 用 `exec logcat` 后进程名已变，`pgrep 脚本名` 找不到 | 改匹配 `logcat -b main` |
| 换行符 | CRLF 导致 `sh: syntax error: '}' unexpected` | 强制 LF（`.gitattributes`） |
| 车机时钟 | 车机为 UTC，目录名比本地时间少 8 小时 | `start` 第二参数传入 PC 时间戳 |
| 存储 | `/sdcard` 约 4GB 可用 | 脚本内置 600MB 自动停止保护 |

## 8. 已知限制

1. **无 Binder Payload**：只有元信息，字段级内容需靠各方日志或标定试发。
2. **无 root 时**：只能用 PC 端脚本，抓不到 Binder 事务。
3. **`events` 缓冲**：部分设备上格式混杂，若影响可临时去掉 `-b events`。
4. **进程重启**：pid 会变，跨重启分析需用 `binder_pids.txt` 的分段快照对齐。

## 9. 与代码修复的关系

本文档只负责**取证**。基于同一批证据得出的代码修复记录在 20 号文档：

- 罗盘帧保活重发导致外圈闪烁 → 罗盘帧不再 keepalive
- 高德交替下发"全零"10001 帧 → 零值不再覆盖上一帧
- 导航中缺失 ICON 被判为无转向 → 保留上一图标；罗盘仅非导航时出现
- 数据空档 4~5 秒 vs 3 秒超时 → 超时放宽至 8 秒
- 纯地图态无航向 → 新增车机 GPS 航向兜底（`GpsHeadingProvider`）
- 左右相反 → `mapTurnType` 左右成对镜像
